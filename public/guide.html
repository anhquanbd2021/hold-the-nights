Lab guide

The index can lie for thirty seconds. The calendar cannot.

This demo exists because the double-booking bug is the part every whiteboard skips. Six scripted races make the one asymmetry legible: everything above the calendar is a copy, and the calendar is the only component that genuinely needs a lock.

A model, not a database. The lab replays deterministic interleavings in memory — no real Postgres, payment gateway, or network. It makes the mechanism visible; it does not replace it.

The lab, feature by feature

What each piece proves

Scenario picker

Six races, one asymmetry

Each button replays a scripted interleave of two guests chasing the same four nights: check-then-insert, charge-first, the UNIQUE constraint, hold-then-pay, hold expiry, and a thirty-second-stale index.

Proves
The order of operations — not any single statement — decides whether the night is double-booked.
Key detail
Every scenario replays deterministically; the outcome is derived from the final calendar and ledger, never declared.
Search index

A copy that is allowed to lag

The index panel keeps advertising open nights after the room is gone — a read-optimized projection rebuilt from the calendar, never consulted on the write path.

Proves
Search results are advertising, not inventory. A stale copy harms no one because copies stay off the write path.
Key detail
In the search-lag race the index is 30 seconds stale, says "open," and the calendar still rejects the loser cleanly.
Calendar

One row per night — the only truth

The calendar is the one component two guests can fight over at the same instant. Watch each night flip open → held → booked — or open → booked → double.

Proves
The calendar is the only thing in the system that genuinely needs a lock.
Key detail
A night with two entries in bookedBy is the double-booking — the impossible state made visible.
Ledger

Who paid what, and when

Charges and refunds land in the ledger as the race runs, so you can see money move before the lock — the pay-first anti-pattern.

Proves
Charge first and the loser exits through a refund queue: money taken for a room somebody else got.
Key detail
Hold-then-pay ends with the loser rejected before a cent moves — the failure price drops to "show different dates."
Replay controls

Step the gap between check and write

Play, Step, and Reset walk the race one event at a time. Stepping exposes the exact instant where the world changes between the read and the write.

Proves
Check-then-insert is a TOCTOU bug: no single statement lied — the gap between statements did.
Key detail
Both guests can read "every night free" and both be right; two unconstrained writes later, every night has two owners.
The trace

Every event, flagged in place

The trace narrates each op — searches, checks, holds, charges, writes, expiries — and flags stale reads, conflicts, and failures inline.

Proves
A UNIQUE index saves the row at write time, not the guest — the database is right and the business is still wrong.
Key detail
Holds die on their own: when the clock passes expires_at the lock stops counting — no sweeper required for correctness.

Run locally

Inspect the evidence

npm test        # lock semantics + race outcomes + e2e server routes
npm run check   # alias for npm test
npm start       # serve the lab on :3000

The domain model is erasable-syntax-only TypeScript — the same file the tests exercise is the file the browser runs.

Limits

What this demo does not claim

  • The races are scripted replays, not a live booking system — no real database, payment gateway, or network between guests.
  • The atomic hold mirrors what INSERT … ON CONFLICT or SELECT … FOR UPDATE gives you; the point is to make the mechanism legible, not to replace Postgres.
  • Idempotency keys, 3-D Secure, and multi-region writes are named in the article but intentionally left out of the model.
  • All guests, listings, and amounts are fixtures. Nothing here is production infrastructure.
